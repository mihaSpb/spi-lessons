# Подключение MAX к AI-агенту: официальный и неофициальный способы

> Актуальность исходной инструкции: 3 сентября 2026 года. MAX быстро меняется. Перед установкой агент обязан свериться с актуальной официальной документацией и свежими версиями выбранных библиотек.

Эта инструкция предназначена для AI-агента. Пользователь отдаёт агенту файл целиком и пишет: «Прочитай инструкцию и проведи меня по подключению MAX».

---

## Главное правило: сначала выясни задачу и способ

Когда пользователь просит «подключи MAX», «интегрируйся с MAX» или «дай читать мои сообщения MAX», **не начинай установку сразу**.

Сначала задай пользователю два коротких вопроса простыми словами:

1. **Что вы хотите читать?**
   - обычные личные переписки вашего аккаунта, включая старую историю;
   - только сообщения, которые люди присылают отдельному боту, и сообщения из групп/каналов, куда добавлен бот;
   - пока не уверены — нужно помочь выбрать.
2. **Какой способ вы выбираете?**
   - официальный Bot API — безопаснее, но не видит личные переписки пользовательского аккаунта;
   - неофициальная пользовательская сессия — видит личные чаты и историю, но нарушает правила MAX и может привести к ограничению аккаунта;
   - сначала показать сравнение и помочь выбрать.

Если пользователь просит помочь выбрать, объясни в трёх фразах:

- **Официальный способ** создаёт отдельного бота. Он видит только свой диалог с пользователем и те группы или каналы, куда его добавили с нужными правами.
- **Неофициальный способ** подключается как ещё одно устройство пользовательского аккаунта и поэтому способен читать обычные чаты и историю.
- Неофициальная автоматизация и обратная разработка запрещены пунктом 4.3.7 Пользовательского соглашения MAX. Есть риск поломки после обновления протокола, отзыва сессии или ограничения аккаунта. Предупреди об этом, но **не принимай решение вместо пользователя и не блокируй подключение**, если пользователь явно выбирает этот путь.

Зафиксируй выбранный способ в ответе одной строкой и выполняй только соответствующую ветку ниже.

# Ветка А. Официальный Bot API

## Когда этот способ подходит

Выбирай официальный способ, если пользователю достаточно:

- читать новые сообщения, отправленные непосредственно боту;
- читать сообщения группы или канала, куда бот добавлен и получил право `read_all_messages`;
- отвечать от имени бота;
- построить поддержку, приём заявок, уведомления или рабочий групповой процесс.

Сразу скажи об ограничении: официальный Bot API **не получает личные диалоги между пользовательским аккаунтом владельца и другими людьми**. Он также не превращает бота в копию личного аккаунта.

### Почему не используем официальный Open Client API

У MAX существует отдельный Open Client API для полноценных пользовательских приложений: https://legal.max.ru/openclient-docs

Он не является обычной заменой Bot API. Доступ выдаётся участникам программы после заявки, проверки и получения App-ID. Публичные условия на дату инструкции допускают к заявке юридические лица, отвечающие требованиям программы: https://legal.max.ru/openclient-apply

Кроме того, клиент должен работать непосредственно на устройстве пользователя. Условия запрещают передавать данные через backend, прокси, шлюзы и сторонние сервисы, а также запрещают автоматизированный сбор, массовую выгрузку, индексирование, создание архивов и передачу пользовательских данных в системы машинного обучения. Поэтому Open Client API не подходит для обычного подключения облачного AI-агента к личной истории MAX.

Не предлагай обходить эти ограничения. Если у пользователя есть подходящее юридическое лицо и он хочет разработать отдельный официальный клиент, предложи подать заявку и дождаться App-ID, полной технической документации и письменного согласования нужного сценария. До одобрения не обещай доступ к методам пользовательской истории.

## Шаг 1. Сверь актуальную документацию

Открой и проверь:

- обзор API: https://dev.max.ru/docs-api
- создание и модерация бота: https://dev.max.ru/docs/chatbots/bots-create/create
- получение токена: https://dev.max.ru/docs/chatbots/bots-create/manage
- Long Polling: https://dev.max.ru/docs-api/methods/GET/updates
- Webhook: https://dev.max.ru/docs-api/methods/POST/subscriptions
- типы событий: https://dev.max.ru/docs-api/objects/Update
- получение сообщений: https://dev.max.ru/docs-api/methods/GET/messages
- права администратора: https://dev.max.ru/docs-api/methods/POST/chats/-chatId-/members/admins
- история изменений API: https://dev.max.ru/docs-api/changelog-api

Проверь текущий домен API, требования к сертификатам, лимиты запросов, названия событий и ограничения методов. На дату этой инструкции рабочий домен — `https://platform-api2.max.ru`, токен передаётся только в заголовке `Authorization`.

Если документация отличается от этой инструкции, покажи пользователю различия и следуй свежей официальной документации.

## Шаг 2. Проверь возможность создать бота

Для создания официального бота нужен верифицированный профиль на платформе MAX для партнёров. На дату инструкции подключение доступно организациям, ИП и самозанятым — резидентам РФ.

Попроси пользователя:

1. Открыть платформу MAX для партнёров или мини-приложение «MAX для бизнеса».
2. Войти в нужный профиль.
3. Проверить, что профиль верифицирован.
4. Открыть раздел «Чат-боты» и нажать «Создать».

Не проси логин, пароль, SMS-код или доступ к Госуслугам. Все чувствительные действия пользователь выполняет сам в интерфейсе MAX.

## Шаг 3. Создай и промодерируй бота

Проведи пользователя по карточке бота:

1. Название — понятное назначение, например «Личный помощник Михаила».
2. Логотип — квадратное изображение по текущим требованиям MAX.
3. Описание — что бот читает и для чего используется.
4. Телефон и сайт — только если действительно нужны.
5. Отправить бота на модерацию.

На дату инструкции модерация может занимать до 48 часов по рабочим дням. Не обещай мгновенное подключение. После одобрения открой «Расширенные настройки → Настроить» и попроси пользователя самостоятельно скопировать токен.

## Шаг 4. Безопасно сохрани секреты

До сохранения токена:

1. Найди корень рабочей папки.
2. Добавь `.env`, файлы сессий и локальные секреты в `.gitignore`.
3. Выполни `git check-ignore .env` и убедись, что файл игнорируется.
4. Только после этого сохрани токен.

Рекомендуемые переменные:

```dotenv
MAX_BOT_TOKEN="значение-токена"
MAX_WEBHOOK_SECRET="случайная-строка-минимум-5-символов"
```

Значения не печатай в чат, логи, Markdown, скриншоты или Git. В отчёте показывай только `MAX_BOT_TOKEN: задан` или `не задан`.

## Шаг 5. Проверь токен безопасным запросом

Подгрузи `.env` внутри процесса и вызови:

```bash
curl -fsS "https://platform-api2.max.ru/me" \
  -H "Authorization: $MAX_BOT_TOKEN"
```

Не включай shell tracing (`set -x`) и не печатай заголовок авторизации. Успешный ответ должен содержать данные созданного бота и `is_bot: true`.

Если пришёл `401`, не проси новый токен в открытом чате: предложи пользователю проверить токен в настройках бота и безопасно заменить значение в `.env`.

## Шаг 6. Подключи источники сообщений

### Личный диалог пользователя с ботом

Пользователь должен открыть ссылку бота и нажать кнопку начала общения. После этого бот получает события `bot_started` и новые сообщения `message_created`.

Это диалог **пользователь ↔ бот**, а не личная переписка пользовательского аккаунта с другими людьми.

### Групповой чат

1. Пользователь добавляет бота в нужную группу.
2. Администратор назначает бота администратором.
3. Боту дают право `read_all_messages`.
4. Если нужна только функция чтения, не выдавай права `write`, `delete`, `add_admins` и другие лишние разрешения.
5. Проверь права методом `GET /chats/{chatId}/members/me` или через список администраторов.

Без `read_all_messages` бот не будет получать все сообщения группы через Webhook.

### Канал

Добавь бота в канал и назначь только необходимые права. Для чтения постов требуется `read_all_messages`. Не выдавай права публикации и удаления, если пользователь просил только чтение.

## Шаг 7. Выбери доставку новых сообщений

Спроси пользователя, что нужно:

- локальная проверка или разработка — Long Polling;
- постоянная рабочая интеграция — Webhook.

### Вариант 7А. Long Polling для тестирования

Используй `GET /updates`.

Основные параметры:

- `limit`: 1–1000, по умолчанию 100;
- `timeout`: 0–90 секунд, по умолчанию 30;
- `marker`: указатель из предыдущего ответа;
- `types`: например `message_created,bot_started,bot_added,message_edited,message_removed`.

Важно:

- без `marker` MAX возвращает только последнее обновление;
- после передачи `marker` предыдущие события считаются прочитанными;
- Webhook и Long Polling одновременно не работают;
- Long Polling ограничен по скорости и сроку хранения событий и не подходит для production.

Для первого теста запроси последнее событие, затем сохрани полученный `marker`. После этого отправь боту тестовое сообщение и запроси обновления с сохранённым маркером.

### Вариант 7Б. Webhook для постоянной работы

Перед развёртыванием спроси явное разрешение пользователя: Webhook — это внешний сервер и постоянная интеграция.

Требования MAX:

- публичный HTTPS endpoint;
- только порт 443;
- действующий сертификат доверенного центра, самоподписанный сертификат не подходит;
- домен совпадает с CN/SAN сертификата;
- сервер отдаёт полную цепочку сертификатов;
- endpoint отвечает `HTTP 200` не позднее 30 секунд;
- секрет передаётся в заголовке `X-Max-Bot-Api-Secret` и должен проверяться до обработки тела;
- при ошибке MAX выполняет до десяти повторных попыток;
- если успешного ответа нет восемь часов, MAX автоматически удаляет подписку.

Подписка создаётся через `POST /subscriptions`:

```json
{
  "url": "https://example.ru/max/webhook",
  "update_types": [
    "message_created",
    "message_edited",
    "message_removed",
    "bot_started",
    "bot_added",
    "bot_removed"
  ],
  "secret": "значение-из-MAX_WEBHOOK_SECRET"
}
```

Webhook сначала валидирует секрет, быстро сохраняет событие и возвращает `200`; тяжёлую обработку выполняй после подтверждения приёма. Обрабатывай дубли идемпотентно: одно событие может прийти повторно.

Не создавай cron, systemd, PM2 или иной постоянный процесс без отдельного согласия пользователя и понятного способа остановки.

## Шаг 8. Организуй чтение истории

Для новых сообщений источником истины являются события `message_created`, `message_edited` и `message_removed`. Сохраняй минимум:

- тип события;
- `chat_id`;
- ID сообщения (`mid` или соответствующее поле актуальной схемы);
- отправителя;
- точный timestamp;
- текст;
- типы и идентификаторы вложений;
- связь с ответом или пересылкой;
- отметку об изменении или удалении.

Для групп и каналов, где бот является администратором, используй `GET /messages?chat_id=...`:

- `count` — до 100 сообщений за запрос;
- `from` и `to` — Unix timestamp в миллисекундах;
- сообщения возвращаются от новых к старым.

Не обещай полный backfill личного диалога с ботом, пока это не подтверждено актуальной документацией. Если метод не отдаёт историю диалога, доступна только история, которую интеграция получила и сохранила через события, плюс отдельные сообщения по известным `message_ids`.

С июня 2026 года `GET /chats` не предоставляет готовый список групп и каналов. Поддерживай собственный реестр `chat_id` из событий `bot_added`, `bot_started`, `bot_removed` и других обновлений.

## Шаг 9. Дай агенту read-only инструменты

Создай минимальный локальный skill или MCP с безопасными командами:

- `max_list_bot_chats` — список известных чатов бота из локального реестра;
- `max_read_bot_messages(chat_id, limit, before)` — чтение сохранённых событий и разрешённой истории;
- `max_search_bot_messages(chat_id, query)` — локальный поиск;
- `max_get_bot_chat(chat_id)` — данные чата и текущие права бота.

Не добавляй отправку, редактирование или удаление сообщений, пока пользователь отдельно не попросит об этом.

## Шаг 10. Проверь официальный способ

Выполни проверку по порядку:

1. `GET /me` возвращает правильного бота.
2. Пользователь пишет боту уникальную тестовую фразу.
3. Интеграция получает `message_created` и показывает автора, время и текст.
4. В тестовой группе бот с `read_all_messages` получает сообщение другого участника.
5. Повторная доставка события не создаёт дубль.
6. После перезапуска сохранённый `marker` или Webhook-регистр продолжает работу.
7. Агент по просьбе «прочитай последние сообщения MAX-бота» возвращает только данные разрешённых чатов.
8. Ни одного секрета нет в Git, логах и выводе.

## Типичные ошибки официального способа

| Ошибка | Что проверить |
|---|---|
| `401 Unauthorized` | токен бота, заголовок `Authorization`, отсутствие пробелов и переносов |
| `403 Forbidden` | пользователь остановил бота, бот не участник чата или ему не выданы права |
| Нет событий группы | бот администратор и имеет `read_all_messages` |
| Long Polling ничего не возвращает | активен Webhook, потерян `marker`, неверно заданы `types` |
| Webhook не вызывается | HTTPS, порт 443, сертификат, цепочка сертификатов, доступность URL |
| Подписка исчезла | endpoint не возвращал `200` в течение восьми часов |
| Не видны старые личные переписки | это ограничение Bot API, а не ошибка установки |
| Не получается получить список чатов | `GET /chats` больше не поддерживает готовый список; собирай `chat_id` из событий |

## Что сказать пользователю в конце официального подключения

Сообщи:

- имя и ID бота;
- какие диалоги, группы и каналы реально доступны;
- какие права выданы;
- используется Long Polling или Webhook;
- где лежит локальный реестр сообщений;
- какими фразами просить агента читать сообщения;
- что личные пользовательские переписки по-прежнему недоступны.

# Ветка Б. Неофициальная пользовательская сессия

## Когда этот способ нужен

Эта ветка нужна, если пользователь хочет:

- видеть обычные личные чаты своего аккаунта;
- читать старую историю;
- искать по перепискам;
- читать группы и каналы так же, как в приложении MAX;
- обращаться к MAX через AI-агента примерно так же, как к Telegram через пользовательскую библиотеку.

Техническая основа — reverse-engineered клиент внутреннего протокола MAX, например:

- `max-mcp`: https://github.com/renosaza/max-mcp
- PyMax: https://github.com/MaxApiTeam/PyMax
- документация PyMax: https://docs.pymax.org/

Это **не официальный API MAX**.

## Шаг 1. Объясни риск и получи решение пользователя

Скажи простыми словами:

> Этот способ входит в MAX как дополнительное устройство вашего аккаунта и поэтому может читать личные чаты. Он неофициальный: протокол получен обратной разработкой. Пункт 4.3.7 Пользовательского соглашения MAX запрещает автоматизированные скрипты для извлечения информации и обратную разработку. Возможны поломки после обновлений, отзыв сессии или ограничение аккаунта. Продолжать?

Ссылка на соглашение: https://legal.max.ru/ps

Если пользователь отказался — останови эту ветку и предложи официальный Bot API.

Если пользователь явно согласился — продолжай. **Предупреждение не является автоматическим запретом:** выбор делает пользователь.

Отдельно спроси, какой аккаунт использовать:

- тестовый аккаунт — безопаснее для проверки, но он не увидит личные чаты основного аккаунта;
- основной аккаунт — даст нужные переписки, но несёт максимальный риск.

## Шаг 2. Проверь актуальность проектов

Перед установкой:

1. Открой README, releases, последние commits и открытые issues `max-mcp`.
2. Проверь актуальную версию `maxapi-python` на PyPI и совместимость с текущим PyMax.
3. Посмотри последние проблемы авторизации, сертификатов, формата сообщений, изображений и ошибки `unsupported client version`.
4. Проверь лицензию каждого компонента.
5. Не устанавливай случайный fork только потому, что он обещает больше функций.

На дату исходной инструкции upstream `max-mcp` использовал `maxapi-python 2.1.2`, а PyMax развивался дальше. Поэтому не обновляй зависимость вслепую: сначала запусти тесты upstream, затем отдельно проверь совместимость новой версии.

## Шаг 3. Сделай локальный аудит безопасности

До QR-входа изучи исходный код:

- куда отправляются сетевые запросы;
- где хранится сессия;
- нет ли отправки токенов, QR, сообщений и файлов на сторонние серверы;
- нет ли `eval`, скрытых subprocess-команд, телеметрии и загрузки исполняемого кода;
- какие каталоги доступны инструментам отправки файлов;
- зафиксированы ли версии и хеши зависимостей.

Установка должна быть локальной. MCP работает через `stdio`, не открывает публичный порт и не передаёт сессию стороннему MCP-хостингу.

Если аудит обнаружил неизвестный внешний endpoint или отправку сессии третьей стороне, остановись и покажи находку пользователю.

## Шаг 4. Создай read-only fork

Пользователь просит чтение, поэтому минимизируй полномочия:

1. Создай локальный fork `max-mcp` в каталоге интеграций проекта.
2. Удали регистрацию `send_message` и `send_file` из MCP-сервера либо поставь их за явный выключенный флаг.
3. Не добавляй команды удаления, редактирования, реакций и отметки о прочтении.
4. Оставь:
   - `list_chats`;
   - `get_chat`;
   - `read_messages`;
   - `search_messages`;
   - `list_channel_posts`;
   - при необходимости — безопасное скачивание выбранного вложения.
5. Для скачивания разреши только отдельный каталог пользователя; запрети `.ssh`, `.aws`, каталоги сессий, системные каталоги и симлинки.

Если пользователь позже захочет отправлять сообщения, это отдельное расширение: сначала покажи точный `chat_id`, получателя и текст, затем запроси подтверждение отправки.

## Шаг 5. Защити пользовательскую сессию

Сессия по силе близка к входу в аккаунт. Не храни её в репозитории.

Рекомендуемый путь на macOS:

```text
~/Library/Application Support/CyberOS/max/
```

Требования:

- каталог `0700`;
- файл сессии `0600`;
- владелец — текущий пользователь;
- каталог и файл не являются симлинками;
- путь исключён из Git;
- содержимое сессии никогда не читается в чат и не попадает в логи;
- резервная копия создаётся только по отдельному решению пользователя и хранится зашифрованно.

Если upstream жёстко использует `~/.max-mcp/`, добавь в fork настройку `MAX_MCP_SESSION_DIR`, а не копируй сессию между каталогами вручную.

## Шаг 6. Установи зависимости воспроизводимо

Проверь наличие Python и `uv`:

```bash
python3 --version
uv --version
```

Для upstream требовался Python 3.11–3.13. Используй lock-файл:

```bash
uv sync --frozen
```

Запусти тесты до авторизации:

```bash
uv run --with pytest --with pytest-asyncio python -m pytest -q -p no:cacheprovider
```

Если тесты не проходят, не переходи к QR-входу. Исправь окружение или код, повтори тесты и покажи пользователю фактический результат.

## Шаг 7. Авторизуй устройство по QR-коду

Предпочтительный способ — QR, потому что пользователь подтверждает новое устройство внутри официального приложения MAX.

Команда upstream:

```bash
uv run max-mcp-login login-qr
```

Дальше:

1. Покажи QR только локально в терминале пользователя.
2. Попроси пользователя открыть в мобильном MAX раздел привязки или активных устройств; название пункта сверяй с актуальным интерфейсом.
3. Пользователь сканирует QR самостоятельно.
4. Не делай скриншот QR и не пересылай его.
5. После входа проверь права каталога и файла сессии.
6. В официальном MAX покажи пользователю появившееся устройство и объясни, как отозвать его.

Вход по телефону и SMS используй только если QR не работает и пользователь сам выбирает этот вариант. Код и пароль двухфакторной защиты пользователь вводит локально, они не сохраняются в Markdown или логах.

## Шаг 8. Подключи MCP к агенту

Добавь локальный MCP-сервер в канонический конфиг текущего агента. Не угадывай файл конфигурации: сначала найди документацию среды и существующий формат проекта.

Команда запуска должна использовать абсолютный путь и локальный `stdio`, например:

```text
uv run --directory /абсолютный/путь/к/max-mcp max-mcp
```

После изменения конфигурации:

1. проверь синтаксис;
2. перезапусти MCP-клиент или сессию агента;
3. убедись, что появились только read-only инструменты;
4. не запускай постоянный фоновый listener без отдельного разрешения пользователя.

## Шаг 9. Проверь чтение без побочных действий

Используй тестовый чат с уникальной фразой.

Проверка:

1. `list_chats(limit=20)` возвращает список чатов.
2. Найди тестовый чат по названию и зафиксируй его `chat_id`.
3. `read_messages(chat_id, limit=20)` возвращает сообщения от новых к старым.
4. Проверь автора, точное время, текст и reply-связь.
5. `search_messages(query, chat_id, scan_limit=500)` находит уникальную тестовую фразу.
6. Проверь сообщение с картинкой, документом, голосовым и пересылкой — эти типы чаще ломаются после изменения протокола.
7. Убедись, что чтение не вызвало отправку, удаление, реакцию или изменение сообщения.
8. Отдельно проверь, меняется ли отметка «прочитано». Если библиотека автоматически помечает чат прочитанным, честно сообщи пользователю и не называй режим полностью пассивным.

Не начинай с массовой выгрузки всей истории. Сначала 20 сообщений одного тестового чата, затем один реальный чат по выбору пользователя.

## Шаг 10. Создай понятный skill MAX

Skill должен срабатывать на фразы:

- «прочитай переписку в MAX с …»;
- «что нового в MAX»;
- «найди в MAX сообщение про …»;
- «покажи последние сообщения чата MAX …».

Правила skill:

1. По умолчанию только чтение.
2. Сначала найти чат по точному названию или идентификатору.
3. При совпадении нескольких чатов показать варианты, не угадывать.
4. Не читать больше сообщений, чем нужно для ответа.
5. Не выгружать все чаты без прямого запроса.
6. Не показывать сессию, токены и внутренние данные авторизации.
7. Сохранять источник: `chat_id`, ID сообщения и точное время.
8. Перед скачиванием вложения показать имя, тип и размер.
9. Отправка всегда выключена, пока пользователь отдельно её не разрешил.

## Шаг 11. Обработай типичные поломки

| Симптом | Действие |
|---|---|
| QR принят, но команда завершилась `CancelledError` | проверь, создана ли сессия; обнови обработку штатной остановки после входа |
| `unsupported client version` | MAX изменил требования к версии клиента; обнови PyMax после проверки release/issues |
| Ошибка UTF-8 на сообщении с картинкой | обнови нормализацию бинарных вложений; не декодируй произвольные байты как UTF-8 |
| Ошибка сертификата | проверь свежий сертификат и цепочку; не отключай TLS-проверку глобально |
| Часть чатов отсутствует | выполни актуальный `fetch_chats`; кеш после login не гарантирует полный список |
| Сессия отозвана | покажи пользователю устройство в MAX, удали только точный локальный файл сессии и повтори QR-вход |
| После обновления пропала история | останови интеграцию, проверь changelog и issues; не запускай массовые повторные запросы |
| MCP не появился | проверь абсолютный путь, команду запуска, stderr и перезапуск агента |

## Шаг 12. Настрой остановку и откат

Пользователь должен уметь полностью отключить интеграцию:

1. Остановить MCP-процесс.
2. Удалить запись MCP из конфигурации агента.
3. В приложении MAX открыть активные устройства и отозвать созданную сессию.
4. После подтверждения отзыва удалить **только конкретный** файл локальной сессии и marker-файлы.
5. Не удалять широкие каталоги, домашнюю папку или рабочий репозиторий.
6. Проверить, что read-only инструменты MAX исчезли после перезапуска агента.

## Что сказать пользователю в конце неофициального подключения

Сообщи:

- какой аккаунт подключён: тестовый или основной;
- что способ неофициальный и пользователь принял риск;
- где хранится сессия, не раскрывая её содержимое;
- какие read-only инструменты доступны;
- проверены ли текст, поиск и вложения;
- меняет ли чтение отметку «прочитано»;
- как отозвать устройство и отключить интеграцию;
- какими фразами просить агента читать MAX.

# Финальная проверка для обоих способов

Перед завершением агент обязан проверить:

- [ ] пользователь осознанно выбрал официальный или неофициальный способ;
- [ ] доступ соответствует задаче пользователя;
- [ ] официальная документация или актуальные репозитории перечитаны;
- [ ] секреты и сессии находятся вне Git и не попали в вывод;
- [ ] подключение началось с минимальных прав и режима только для чтения;
- [ ] тестовое сообщение действительно прочитано;
- [ ] автор, время и текст определяются корректно;
- [ ] известны ограничения истории и вложений;
- [ ] пользователь знает, как отключить интеграцию;
- [ ] создан короткий документ или skill с рабочими командами;
- [ ] в итоговом отчёте нет токенов, QR-кодов, SMS-кодов и содержимого файла сессии.

Главный критерий готовности: пользователь может написать агенту «прочитай последние сообщения в MAX», агент находит нужный разрешённый чат, показывает сообщения с автором и временем и не совершает никаких действий записи.
